**Встречные вопросы владельца и вердикты (2026-09-07, после этапа 6; только документация, код не менялся):**
1. **«Разве форк использует dll-native базу — не коллекторные ли наши БД?»** — Использует и то, и другое. Коллекторные БД (`databases/<Name>/`, GPU-декод, создаются NvJpegCollector.exe) — продуктовая модель форка. Но унаследованная внутренняя БД оригинального AntiDupl.NET тоже жива: пункт меню «Использовать базу данных о картинках» (`useImageDataBase=true` по умолчанию, `Options.cs:65`), пишет в `<UserPath>\images\<N>x<N>\` (DLL-native формат «adii»), путь отличен от коллекторных. Эмпирика на машине владельца (bin/Release/user/images/32x32/): 3 чанка, ~32 тыс. записей, 22.4 МБ — подтверждено разбором index.adi (ключи 0/1/2, диапазоны путей реальных библиотек). **Практический вывод:** концепция форка именно та, что описывает владелец — единой внутренней БД продукт не предусматривает, но механизм оригинала физически не удалён и частично исполняется. Что осталось: (i) класс `TImageDataStorage` в DLL общий для двух веток — коллекторской (`Load` → `LoadCollectorNative`/`LoadCollectorData` = загрузчик ваших БД) и dll-native (`SaveIndex`/`SaveData`/`SetOld`/`ClearDatabase` = писатель внутренней БД); (ii) галка меню, `useImageDataBase=true` по умолчанию; (iii) Load/Save/Clear вокруг каждого поиска (`SearchExecuterForm.cs:184-200`); (iv) пункт меню «Удалить неактуальные записи из базы данных о картинках» (работает по внутренней БД); (v) мёртвый UI редактора путей (`CorePathsForm`/onePath — его значения принудительно перезаписываются путями включённых БД в `CoreThreadTask:155-158`, коммит a0935ac от 21.06; запустить поиск по произвольной папке из GUI нельзя — пути только Enabled+Ready из ad_database.xml). **Что реально исполняется:** при DB-поиске Load мёртв (ClearMemory в начале `Search()`, коммит 13ce410 от 20.06 — session-isolation против фантомов) и Save — no-op (`m_needToSave` выставляется только `Get()` из live-скана; коллекторские записи грузятся через `Insert()` без флага). Единственный живой писатель — live-scan fallback: если включённая+Ready БД не загрузилась (например, thumbSize не совпал — до пре-чека 6618a3d от 11.08 такое доходило до поиска), `Search()` сканирует её папку с диска (CPU-декод), и Save пишет все миниатюры в `user\images\<N>x<N>\`. Эмпирика владельца: 3 чанка / 22.4 МБ / даты 21.06, 18.07, 11.08.2026 (диапазоны Youtube-Edit / _porn / Sandy+Sara St James) — три live-scan события, а не «каждый поиск». **Вердикт:** это дефекты legacy-механизма, концептуально уже упразднённого; правильное разрешение — не чинить, а удалить обвязку. Вариант (г) «восстановить пользу предзагрузки» снят как противоречащий концепции. Рекомендация: (в) — убрать Load/Save/Clear из SearchExecuterForm + галку + пункт меню «Удалить неактуальные записи» (коллекторская ветка TImageDataStorage не затрагивается), опционально снести `user\images\`; решение после перерыва.
2. **«О каких массовых переименованиях речь?»** — Формулировка «массовые переименования» неточна, отозвана. Функции пакетного переименования в продукте нет; реальные пути смены пути: единичные Rename из результатов (через CoreLib.Rename) и пакетный Move (MoveSelectedAction, File.Move). Стоимость «перечитывания миниатюр после переименования» — на каждый переименованный файл при следующем поиске, не «массово». И главное: это находка о внутренней БД, которая в концепции форка упразднена (см. п. 1) — чинить её механизмы не нужно; актуальна она может стать только если live-scan fallback сам по себе станет предметом рефакторинга.
3. **«Насколько вероятны экстремальные значения в GPU-пороге?» (лист-2, целочисленное усечение)** — Посчитано; эффект нулевой, закрыто как задокументированное поведение. Формула: `thresholdPerPixel = (td·255)²⁄10000`, td из GUI ограничен 0–15 % (SquaredSum; SSIM — до 50). Переполнение int недостижимо: худший случай (reducedImageSize=128 → thumbSize=16384; td=15 → 1471) ≈ 24 млн ≪ INT_MAX (2.1 млрд); «экстремальные значения» GUI не позволяет задать в принципе. Обнуление порога возможно только при td=0 → thresholdPerPixel=0 → порог 0 («только идентичные») — семантически корректно. Единственный реальный эффект усечения — floor на ~8 % при td=1 (6.5 → 6) и меньше при остальных, причём **идентично** в CPU (`adImageComparer.cpp:53-55`) и GPU (`adEngine.cpp:447-450`) — режимы согласованы между собой, пользовательской дивергенции нет. Переход на double сдвинул бы пороговые пары и потребовал полной ревалидации матрицы — цена больше эффекта.

## Methodology

- **Charter:** `ReviewPrompt.txt` (широкое senior-ревью, новый Audit.md, report-only, без билда).
- **Оркестрация:** unlazy-план `.unlazy/audit-2026-09-05/PLAN.md` (rev 3: после гибели двух волн субагентов от лимита 8 req/min драйвер исполнял листы последовательно сам).
- **Каждый лист:** полное чтение файлов подсистемы → находки с цитатами `путь:строка` → формальная верификация (`scripts/verify-report.mjs`, включая режим `--citations` — проверка существования файла и достаточности строк).
- **Интеграция (node-1):** все шесть листов проходят G1 вместе; все цитаты шести листов проверены `scripts/verify-multiple-citations.mjs`.
- **Диск:** измерение `Get-ChildItem -Recurse` по каждой записи верхнего уровня, категории разбивают записи без пересечений, сумма сверена (`.unlazy/audit-2026-09-05/disk-report.json`).
- **Независимость:** старые `Audit.md`, `Audit/`, `PROJECT_CONTEXT.md`, `IMPLEMENTATION_PLAN.md` не использовались как источник фактов; совпадения с ними (например, jpegPeaks) независимо перепроверены по коду (`src/AntiDupl/AntiDupl.h:552-565`, контракт-пин 69240B в `tests/AntiDupl.Contract.Tests/Program.cs:180`).

|------|-------|------|

| C#-биндинги | `src/AntiDupl.NET.Core/` | P/Invoke (`src/AntiDupl.NET.Core/Original/CoreDll.cs`), `CoreLib`-обёртка, `DynamicModule` загрузка DLL |

## Opinion and proposals

**Мнение.** Кодовая база здорова по архитектуре (дисциплина потоков, RAII, контракт-тесты как идея) и больна в двух местах: (а) **систематические ошибки на границах форматов/каналов/структур** — старшие находки это «данные прошли через границу и тихо исказились»; (б) **тихие отказы** — обрезка результатов, ноль-при-ошибке, глотание экспортов, MessageBox-в-невидимом-окне. Оба класса — плата за скорость развития форка без интеграционной валидации. При этом ни одна из находок не требует переписывания: почти все фиксы — точечные, от 1 строки до одного экрана. Важная поправка от практической проверки 2026-09-05: дефолтный GPU-сценарий (AllVsAll) корректен — статический анализ переоценил P1-3; перед правками кода ключевые гипотезы (R/B-каналы, realloc-wipe) стоит подтверждать управляемыми тестами.

**Предложения (по убыванию ценности):**

1. **Сначала каналы (P1-1, P1-2), потом всё остальное.** Оба фикса — по 1-2 строки, но оба меняют содержимое всех существующих БД. Делать их до любых других изменений, чтобы пересборка БД была одна. После фиксов — обязательная полная пересборка всех БД (команда update с force-режимом или full rebuild).
2. **GPU-доверие (P1-4/5 + P2-4/5/6 + P2-16) как один пакет:** полосовой AllVsAll, fail-fast при CUDA-ошибках, sanity→DisableGpu, перезаливка после realloc (или preallocated), удаление/консолидация мёртвого `UpdateGpuDatabase`. Это один принцип: «GPU-результат без подтверждённого успеха — не результат».
3. **Реестр БД — один писатель (P1-6 + лист-4):** экранирование+декодирование сейчас, единый модуль позже. Три писателя одного файла — мина с длинным фитилём.
4. **CI: contract tests + native-DLL-проверка в Publish (P2-13/14/15)** — четыре строки YAML, закрывающие целый класс регрессий, найденных этим аудитом.
5. **Диск: не удалять, а разложить.** (а) `vcpkg` buildtrees/packages/downloads (~9 GB) — снести или перенаправить кэш в `%LOCALAPPDATA%` (vcpkg поддерживает `VCPKG_DEFAULT_BINARY_CACHE`); (б) stray `src/bin`, `src/obj` (726 MB) — удалить (старые layout'ы, не используются текущими билдами — AGENTS.md); (в) `bin/Debug`, `out/Publish`-старье (~1 GB) — удалить, `bin/Release` оставить (там тестовые БД!); (г) `git gc` (1.26 GiB loose → пакеты). Итог: ~20 GB → **~4-6 GB** без потери чего-либо ценного. **Не трогать:** `bin/Release/databases/`, `src/vcpkg_installed` (нужен для билда с `VcpkgManifestInstall=false`-схемой), vendored vcpkg-клон как таковой (порты).
6. **Мелочи пачкой (P2/P3),** после основных: hash≠0, volatile-флаги, ConcurrentDictionary, фоновый move, [FATAL]-режим коллектора. Каждое — <30 минут.
